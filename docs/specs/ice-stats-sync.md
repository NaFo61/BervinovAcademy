# ТЗ: общий учёт занятий — сайт + бот ICE, разделение менторов

Статус: **IMPLEMENTED** (код в репо; на проде нужен ICE_DATABASE_URL + инвайт TG)

## Зачем

- В Telegram уже работает бот/мини-приложение **pivovarov-ice**: расписание, деньги, статистика.
- Сейчас там ученики **Кирилла** (другой преподаватель). Их нельзя «перевешивать» на вас.
- Нужно, чтобы **вы** тоже вели занятия в этом же боте — со своими учениками.
- На **сайте академии** те же цифры и те же действия: статистика, долги, оплаты, уроки.
- Учёт должен быть **одинаковый** и в боте, и на сайте (не «только сайт» и не «только бот»).

## Что получит человек

1. Вы привязываете свой Telegram → в боте появляется **ваш** кабинет репетитора (отдельно от Кирилла).
2. Ученики Кирилла остаются у Кирилла. Ваши — только у вас.
3. На сайте академии (раздел занятий / финансы) видно **то же**, что в боте: периоды, график, начислено / получено / прогноз, должники, заявки на оплату.
4. Если вы отметили урок или приняли оплату **в боте** — на сайте сразу то же. И наоборот (после действий на сайте).
5. Бот ICE **продолжает работать**; новый бот не поднимаем — используем текущий.

Аккаунт сайта `kuslytuna@yandex.ru` уже **admin** (сделано ранее).

## Решение (делаем так)

| | |
|--|--|
| Движок занятий и денег | **pivovarov-ice** (одна БД, один бот) |
| Сайт академии | второй кабинет: ходит в ICE через **bridge** от имени вашего ментора |
| Разделение менторов | уже есть в ICE (`tutor_id`); Кирилл и вы — разные tutors |
| Привязка | Telegram → ICE user → ваш Tutor; на сайте тот же `telegram_id` связывает academy user ↔ ICE tutor |
| Копирование БД «сайт ← бот один раз» | **не делаем** (иначе снова разъедется) |
| Двусторонняя копия двух баз | **не делаем** (хрупко); вместо этого **одна правда = ICE** |

Итог: бот и сайт читают/пишут **одни и те же** данные ICE. Поэтому цифры всегда совпадают.

## Разбиение на менторов

1. Суперадмин ICE (Кирилл / текущий владелец бота) выдаёт **приглашение репетитора** вам.
2. Вы открываете ссылку в Telegram → активируете Tutor (онбординг: имя, timezone, slug).
3. На сайте: «Привязать Telegram» (уже есть в академии) тем же TG-аккаунтом.
4. Bridge находит ICE tutor по `tg_id` и работает только с **вашими** учениками/деньгами.
5. Admin академии может переключать ментора в UI (если привязано несколько) — чужие данные не смешиваются.

## User stories

1. Как Мирон, я захожу в бот ICE своим Telegram и вижу **пустой/свой** кабинет, не учеников Кирилла.
2. Как Мирон, я на сайте вижу ту же статистику и тех же учеников, что в боте.
3. Как Кирилл, я ничего не теряю: мои ученики и суммы на месте.
4. Как ученик Мирона, я пишу **тому же боту**, но попадаю к Мирону (инвайт / ссылка ментора).

## Acceptance criteria

### Менторы и Telegram

- [ ] В ICE создан активный Tutor для Мирона (через invite), изолированный от Кирилла.
- [ ] Привязка Telegram на сайте связывает academy user ↔ ICE tutor по `tg_id`.
- [ ] Без привязки сайт показывает понятный баннер: «Привяжите Telegram, чтобы открыть кабинет репетитора».
- [ ] Запросы всегда scoped по `tutor_id` текущего ментора (нет утечки чужих учеников).

### Одинаковый учёт (сайт ↔ бот)

- [ ] Статистика на сайте = ICE `GET /api/admin/stats` (from/to, group week|month, buckets, charged/received/forecast, debtors, счётчики уроков).
- [ ] Список уроков / подтверждение оплаты / отметка «проведён» на сайте идут через ICE API того же tutor.
- [ ] После действия в боте обновление на сайте видно после обычного refresh (без рассинхрона двух БД).
- [ ] UI сайта: Неделя / Месяц / Год, листание периода, суммы, столбики, должники (логика как FinanceScreen; стиль академии).

### Бот

- [ ] Текущий бот ICE остаётся рабочим.
- [ ] Не требуем отдельный BotFather-бот для Мирона в этом ТЗ.

## API / bridge (для разработки)

Новый слой в академии, например:

| Метод | Путь | Смысл |
|-------|------|--------|
| GET | `/api/tutoring/ice/status/` | привязан ли TG, есть ли ICE tutor, display_name |
| GET | `/api/tutoring/stats/` | прокси/адаптер → ICE stats (параметры from, to, group, mentor) |
| GET/POST | существующие tutoring endpoints по мере необходимости | либо прокси в ICE, либо тонкий адаптер |

Служебно на сервере академии:

- `ICE_API_BASE_URL`, `ICE_BOT_TOKEN` / сервисный способ вызова API от имени tutor  
  (предпочтительно: academy хранит mapping `user_id → ice_tutor_id` + вызывает ICE internal/service token **или** user-scoped session после TG link; детали реализации в backend-phase, без секретов в git).

Маппинг в БД академии (миграция):

- `TutoringIceLink`: `user` (academy), `ice_tutor_id`, `telegram_id`, `linked_at`.

## Deploy

- ICE: только операции (invite tutor), без ломки текущих данных Кирилла.

- Нужен доступ суперадмина ICE для инвайта Мирона (координация с Кириллом / владельцем бота).
