# FEATURE: Восстановление доступа для входа через VK / Яндекс

Status: **APPROVED**

Одобрено владельцем («делаем»).

---

## Зачем это нужно

Сейчас человек может войти через VK или Яндекс **без пароля** и иногда **без email/телефона**.

Если вход через VK/Яндекс сломается, аккаунт будет трудно вернуть.

Нужно мягко помочь человеку:

1. Сохранить контакт из OAuth (если провайдер его отдал).
2. Предложить задать пароль — **без давления**, не мешая решать задачи.
3. Дать возможность добавить **и email, и телефон** сразу — так безопаснее (два способа восстановить доступ).

---

## Главные правила (как хочет владелец)

- **Не давить.** Нельзя блокировать сайт модалкой, из которой не выйти.
- Легко **пропустить** и идти решать задачи.
- Пароль — только **мягкий баннер** (не агрессивное окно).
- Баннер легко закрыть («Позже» / крестик).
- Контакты по возможности **подтягивать сами**:
  - **VK** → сохранить **телефон**, если VK его отдал.
  - **Яндекс** → сохранить **email**, если Яндекс его отдал.
- **Минимум для «готово»:** пароль + **хотя бы один** контакт (email или телефон).
- **Лучше для безопасности:** заполнить **оба** контакта. Форма и баннер это поддерживают и мягко подсказывают.
- Человек может ввести: только email, только телефон, **или оба сразу**.
- Пароль: soft banner + секция в профиле.

---

## Как сейчас (кратко)

- Вход через VK/Яндекс создаёт пользователя **без нормального пароля**.
- Email с Яндекса иногда уже пишется.
- Телефон с VK **сейчас не сохраняется**, хотя VK может его отдать.
- В профиле email/телефон только смотреть, менять нельзя.
- Задать пароль, будучи уже в аккаунте, **нельзя** (есть только сброс для незалогиненных).
- После OAuth человек попадает в профиль — напоминаний нет.

---

## Что делаем в v1

### 1) Автозаполнение контактов из OAuth

При входе / создании / обновлении через OAuth:

| Провайдер | Что берём | Куда сохраняем |
| --------- | --------- | -------------- |
| VK | телефон, если есть | `User.phone` |
| Яндекс | email, если есть | `User.email` |

Правила:

- Пишем контакт **только если** у пользователя это поле ещё пустое.
- Если контакт уже занят другим аккаунтом — **не перезаписываем чужой**; логируем/пропускаем без падения логина.
- Это сильно снижает число людей «без email и без телефона».
- Один провайдер обычно даёт **один** контакт — второй человек может добавить сам (и оба сразу, если оба пустые).

### 2) Мягкий баннер про пароль

Показываем **тонкий banner** (не blocking modal), если:

- человек вошёл через VK или Яндекс; **и**
- восстановление ещё **не** `ready` (нет пароля и/или нет ни одного контакта).

**Всегда напоминаем**, пока не `ready`. Долгого «спрятать на недели» нет.

Что можно сделать в баннере:

- «Задать пароль» → простая форма (или переход в профиль).
- В той же форме / переходе — поля **email и телефон** (оба видны). Можно заполнить одно, другое или оба. Пустые поля не мешают, если минимум уже есть.
- «Позже» / закрыть → спрятать **только до обновления страницы / новой сессии**. После перезагрузки баннер снова виден, пока не `ready`.
- Всегда можно уйти в каталог / задачи — сайт **не блокируется**.

Копирайт (черновик, спокойный тон):

- Заголовок: «Добавь пароль на всякий случай»
- Текст: «Тогда сможешь войти и без VK или Яндекса. Можно сделать позже.»
- Если нет ни email, ни телефона — короткая подсказка: «Лучше указать и почту, и телефон — так надёжнее. Достаточно и одного.»
- Если есть только один контакт — мягко: «Можно добавить ещё один контакт — так безопаснее.»
- Кнопки: «Задать пароль» / «Позже»

### 3) Секция в профиле

В `#/profile-edit` — блок **«Восстановление доступа»**:

- Показать: есть ли пароль, есть ли email, есть ли телефон.
- Если пароля нет — форма «задать пароль».
- Контакты: **два поля сразу** — email и телефон.
  - Можно заполнить одно, другое или оба за один раз.
  - Уже заполненное поле показать как «есть» (в v1 не меняем).
  - Пустое поле — можно дописать позже.
  - Подсказка: «Можно указать оба — так надёжнее. Для восстановления хватит и одного.»
- Если всё готово (пароль + хотя бы один контакт) — короткий статус: «Можно войти и без VK/Яндекса.»
- Если готов минимум, но второго контакта нет — статус + мягкая строка: «Можно добавить ещё email/телефон.»

### 4) Когда всё «готово»

Считаем восстановление настроенным (`ready`), если:

- есть **нормальный пароль**; **и**
- есть **хотя бы один** контакт: email **или** телефон.

Тогда баннер про «нужен setup» не показываем.

Если контакт уже пришёл из OAuth, а пароля нет — просим **пароль**; поля второго контакта всё равно показываем (необязательно).

«Оба контакта» — **не** условие `ready`, но желательно: UX и API это поддерживают.

---

## Сценарии для человека

1. Вошёл через VK, телефон подтянулся, пароля нет → видит спокойный баннер «добавь пароль» → может закрыть и решать задачи; в форме можно ещё добавить email.
2. Вошёл через Яндекс, email подтянулся → то же: пароль + при желании телефон.
3. Контакта нет → в профиле (или из баннера) вводит email, телефон или **оба** + пароль.
4. Уже есть один контакт → может дописать второй в той же форме (без смены уже заполненного).
5. Нажал «Позже» → баннер скрылся на эту сессию; после обновления страницы снова напоминает, пока не `ready`. В профиле настройка всегда есть.
6. Email/телефон уже занят → понятная ошибка, чужой аккаунт не ломаем.

## Техническая часть (для разработки)

### API: флаги в профиле

В `GET /api/users/me/` добавить:

```json
"recovery": {
  "needs_setup": true,
  "has_usable_password": false,
  "has_email": false,
  "has_phone": false,
  "ready": false
}
```

- `ready` = есть пароль **и** (email **или** phone) — одного контакта достаточно
- `needs_setup` = есть `vk_id` или `yandex_id`, и ещё **не** `ready`
- UI может смотреть `has_email` / `has_phone`, чтобы мягко предложить второй контакт
- В JWT это дублировать не обязательно (v1)

### API: настройка восстановления

`POST /api/auth/recovery/setup/`  
Только для залогиненных (JWT). Лимит запросов — как у login / password-reset.

Тело (поля по необходимости; **email и phone можно передать вместе**):

```json
{
  "password": "NewPass1!",
  "password_confirm": "NewPass1!",
  "email": "user@example.com",
  "phone": "+79001234567",
  "current_password": null
}
```

Правила:

1. Если передали `password` — нужен `password_confirm`, совпадение, `validate_password`.
2. **Один запрос может принять оба контакта сразу** (`email` и `phone` вместе). Также можно только email, только phone, или только password (если контакт уже есть).
3. Минимум для успешного «закрыть дыру»:
   - если пароля нет — нужен пароль в этом или уже существующий usable password;
   - если обоих контактов нет — нужен **хотя бы один** из `email` / `phone` (можно оба).
4. Уже заполненный email/phone этим endpoint **не меняем** (v1). Если передали уже занятое своим значением — ок / no-op; чужое значение → **409**.
5. Пустая строка = поле не передали.
6. Email → нижний регистр; phone — trim; формат как при регистрации.
7. Если после запроса всё ещё нет пароля или нет ни одного контакта — **400** с понятным текстом (не `ready`).

Безопасность:

| Ситуация | Что нужно |
| -------- | --------- |
| Пароля ещё нет, задаём первый | Достаточно JWT |
| Пароль уже есть, меняем | Нужен верный `current_password` |
| Добавляем пустой email и/или phone (один или оба) | Достаточно JWT |
| Смена уже заданного контакта | Не в v1 |

Ответ **200**: тот же private profile, что `/me/`.  
Ошибки: **400** валидация; **401** нет JWT; **409** контакт занят.

### База

- Новых полей на User для v1 **не нужно**.
- Долгого snooze в `localStorage` **нет**: «Позже» только на текущую загрузку страницы (память React). После F5 / новой сессии баннер снова, пока не `ready`.
- Старый ключ `ba_recovery_snooze:<public_id>` при загрузке баннера можно удалить (совместимость).
- Миграции не ожидаются.

### OAuth: куда смотреть в коде

- Создание/логин: `resolve_or_create_user` / OAuth callback.
- VK: scope уже может включать `phone` — **начать писать** в `User.phone`, если пришло и поле пустое.
- Яндекс: email уже часто пишется — проверить и зафиксировать поведение в тестах.

### UI (детали)

- Баннер в общем chrome (`shared.jsx` / app): показывать при `needs_setup`, пока не `ready`; «Позже» — только до обновления страницы.
- Не использовать blocking modal на логине.
- Форма recovery: оба поля контакта видимы; не делать «выбери одно из двух» radio/toggle.
- Стили — как сейчас в SPA.

### Тесты

**Backend:**

1. VK-like user без пароля/контакта → setup password+email → login по email.
2. Без контактов → setup password+email+phone за один запрос → оба сохранены, `ready`.
3. Уже есть email из OAuth → только password → ready; опционально добавить phone вторым запросом.
4. Дубликат email или phone → 409.
5. Без JWT → 401.
6. Уже есть пароль, смена без `current_password` → 400.
7. Флаги `recovery` до/после.
8. Только пароль при пустых контактах → 400.
9. Сохранение phone из VK / email из Yandex при OAuth (если мокаем ответ провайдера).

**Frontend (руками):**

1. OAuth → баннер → «Позже» → сайт доступен → в профиле можно настроить.
2. В форме видны оба поля; можно сохранить один контакт или оба сразу.
3. Успешный setup → баннер пропал → logout → login email+password.
4. «Позже» → баннер скрыт до F5; после обновления снова виден, пока не `ready`.

### Деплой

Обычный `restart.sh` после merge. Env/CI/compose не трогаем. Миграций нет.

## Не делаем в этой фиче

- Жёсткий wizard «сначала пароль — потом сайт»
- SMS / подтверждение email кодом
- Смена уже заданного email/phone
- Требовать оба контакта для `ready` (оба — пожелание, не блокер)
- Google и другие провайдеры
- Долгий snooze (7 дней) и хранение отложения баннера на сервере
- Ломать существующий password-reset / register без нужды
